# UI Content Reference — Network Guardian Dashboard

**Audience:** Anyone reviewing the dashboard against the paper.
**Purpose:** Explain, panel by panel, where every displayed number comes
from and how it is produced.
**Related:** `docs/handoffs/ui_usage_guide.md`,
`docs/handoffs/model_comparison.md`.

---

## 1. Design Principle

Every number the dashboard displays traces to a file produced by the
training or evaluation pipeline. No number is fabricated, hard-coded,
or computed at display time.

The four static JSON files that feed the dashboard are generated by a
single script that reads the trained models and the evaluation outputs.
The script is `scripts/export_ui_data.py`. It is safe to re-run at any
time. It overwrites the four JSON files with fresh copies of the same
data.

---

## 2. The Four Static Data Files

| File | Source | Size | Regenerate with |
|---|---|---|---|
| `client/public/data/class_distribution.json` | `data/processed/split_indices.json` | ~229 bytes | `python scripts\export_ui_data.py` |
| `client/public/data/confusion_matrices.json` | `outputs/03_evaluation/test_predictions.csv` | ~1 KB | same |
| `client/public/data/features.json` | `models/rf_baseline.joblib`, `models/xgb_optuna.joblib`, `models/tabnet_best.zip` | ~2 KB | same |
| `client/public/data/evaluation.json` | `outputs/03_evaluation/test_set_evaluation.json` | ~3.4 KB | same |

Every file uses long model keys: `random_forest`, `xgboost`, `tabnet`.
This matches the `ModelName` type in `client/src/types/index.ts`.

## 3. Panel — Class Distribution

**Displays:** Train and test counts for the five classes.

**Values shown:**

| Class | Train | Test |
|---|---|---|
| normal | 65,874 | 21,958 |
| dos | 40,928 | 13,643 |
| probe | 1,598 | 532 |
| r2l | 749 | 250 |
| u2r | 39 | 13 |

**Source:** `data/processed/split_indices.json`. The counts are
computed once by Notebook 01 and frozen. They are the contract for all
downstream work. If the split is ever regenerated, the frozen hash
check will detect a mismatch.

**Why this replaces a live traffic chart:** the project does not
generate live traffic. This panel shows the actual distribution of the
dataset the models were trained and tested on. It grounds the class
imbalance story in real numbers.

## 4. Panel — Confusion Matrix

**Displays:** The test-set confusion matrix for the currently selected
model. Row = true label. Column = predicted label. Cell = count.

**Values:** derived from `outputs/03_evaluation/test_predictions.csv`.
That file contains one row per test sample and one column per model's
prediction.

**Reading the cells:** diagonal cells are the correct classifications,
highlighted in cyan. Off-diagonal cells are errors, highlighted in
pink. Cell intensity is proportional to the row share, so a row that
mostly classifies correctly shows a bright diagonal cell and faint
off-diagonal cells.

**Example (XGBoost, U2R row):** of the 13 U2R test samples, 10 are
classified as U2R and 3 are misclassified. That matches the paper's
U2R recall of 0.7692.

**What it does not show:** the training-set confusion matrix. The
training-set predictions are available but not surfaced to the UI. The
paper's discussion focuses on the test set.

## 5. Panel — Feature Importances

**Displays:** The top 8 features for the selected model, sorted
descending.

**Values by model:**

### Random Forest — global importance

Extracted from `rf_baseline.joblib` via the model's
`feature_importances_` attribute. This attribute is the mean decrease
in impurity across all trees, averaged over the ensemble.

Top features (as of the current model):

- `service_freq`
- `src_bytes`
- `dst_bytes`
- `logged_in`
- `count`
- `dst_host_diff_srv_rate`
- `srv_count`
- `same_srv_rate`

### XGBoost — global importance

Extracted from `xgb_optuna.joblib` via the same attribute. XGBoost
computes importance differently: it counts the number of times a
feature is used in a split, weighted by the gain of each split.

Top features (as of the current model):

- `flag_S0`
- (remaining seven features as recorded in `features.json`)

The top feature differs from Random Forest's. This is a real finding
worth discussing in the paper. XGBoost relies on the one-hot encoded
`flag_S0` column, while Random Forest relies on the frequency encoding
of `service`. The two models learn different decision boundaries from
the same input.

### TabNet — attention-mask importance

Extracted from `tabnet_best.zip` via the model's `explain()` method on
a 512-row sample of the test set. The method returns a per-row,
per-feature mask. The importance is the mean over the rows.

TabNet's top feature is `service_freq`, matching Random Forest's top
feature. This is a second finding: the tree-based baseline and the
neural network agree on which feature matters most.

**Why only 8 features:** the panel is a top-N view. The full ranking is
available but not displayed. SHAP summary plots for the full ranking
live in the paper's Explainability section.

## 6. Panel — Models View

**Displays:** The frozen test-set comparison table for all three models.

**Values shown:**

| Model | Type | Accuracy | Macro F1 | U2R recall | R2L recall |
|---|---|---|---|---|---|
| XGBoost | Boosting ensemble | 99.90% | 94.51% | 76.92% | 99.20% |
| Random Forest | Bagging ensemble | 99.89% | 93.31% | 76.92% | 95.20% |
| TabNet | Deep learning | 99.76% | 93.06% | 76.92% | 97.60% |

**Source:** `outputs/03_evaluation/test_set_evaluation.json`. This file
was produced by Notebook 03 and has not been modified.

**Key findings surfaced by this table:**

1. **Macro F1 spread is 1.45 points.** XGBoost leads at 94.51%, TabNet
   trails at 93.06%. The ranking is stable across the three models.
2. **U2R recall is identical across all three models at 76.92%.** Ten
   of the thirteen U2R test samples are correctly classified by every
   model. Three are missed by every model. The limit is the data, not
   the model.
3. **R2L recall differentiates.** XGBoost at 99.20% is nearly perfect.
   Random Forest at 95.20% trails by four points. This is the widest
   gap between any two models on any single metric.
4. **Accuracy is uninformative.** All three models are above 99.7%.
   The differences that matter are in the Macro F1 and per-class recall
   columns.

## 7. Panel — Threat Gauge

**Displays:** The live prediction for the most recently submitted
packet.

**Source:** The Express bridge at `POST http://localhost:5000/api/analyze`.
The bridge spawns `predict_bridge.py`, which loads the selected model
and returns a prediction.

**Not static.** This is the only live panel. Every other panel displays
frozen evaluation data.

---

## 8. Panel — Analyze Form

**Displays:** The form for constructing and submitting a network
packet.

**Source:** The field definitions come from
`docs/contracts/api_data_contract.md` section 2. The `NetworkPacketRequest`
interface is defined in `client/src/types/index.ts`.

**Presets:** Three preset packets are defined in `client/src/lib/data.ts`.
They demonstrate normal traffic, DoS, and Probe. The presets are
illustrative — the values are chosen to trigger the correct class, not
sampled from the test set.

## 9. What the Dashboard Does Not Show

Four things a reviewer might expect but should not look for.

- **Training-set metrics.** The confusion matrices and per-class
  recall in the dashboard are test-set values. Training-set metrics
  are in the meta sidecars.
- **Cross-validation metrics.** CV Macro F1 for the three models is in
  `outputs/02_training/model_comparison.csv`, not in the dashboard.
- **SHAP plots.** The SHAP summary plots are in
  `outputs/03_evaluation/shap_summary_rf.png` and
  `shap_summary_xgb.png`. They are not displayed in the dashboard.
- **Training curves.** No learning curves are shown. The models were
  trained with early stopping; the training history is in the Optuna
  study databases.

## 10. Reproducibility

Every number in the dashboard can be reproduced from a clean clone.

1. Clone the repository.
2. Follow `docs/SETUP.md` sections 1 through 9.
3. Run `python scripts\export_ui_data.py`.
4. Start the two servers as described in `docs/handoffs/ui_usage_guide.md`.
5. Open the dashboard.

The four static JSON files are regenerated from the same sources each
time. The numbers match the paper's numbers.
